## Summary

The `transcripttospecs` VS Code agent mode enables platform engineers to convert meeting transcripts into compliant spec drafts in a single Copilot Chat session. The agent operates in three sequential phases: a parallel context-build phase that loads all existing specs upfront and posts a progress banner; a plan-and-clarification phase where the agent proposes tier-category groupings, asks clarifying questions, and resolves conflicts interactively; and a parallel write-execution phase where each confirmed group reports ▶/✓/✗ progress markers and independent writes are batched as parallel tool calls. Two PowerShell toolkit scripts (`register-category.ps1`, `write-spec.ps1`) handle all deterministic file operations; the agent handles all AI reasoning and user interaction.

## Phase 0: Research Summary

All research decisions are documented in `research.md`. Summary:

| Decision | Resolution |
|---|---|
| 1: Execution model split | Agent (reasoning) + scripts (file I/O); no monolithic ingest script |
| 2: AI invocation pattern | VS Code agent mode; no API keys in scripts |
| 3: Data handoff | Agent passes parameters directly to toolkit scripts per session |
| 4: Tier signal vocabulary | 18-entry vocabulary table covering all 6 tiers; lives in analysis template |
| 5: Idempotency | File existence check + spec-id dedup; `register-category.ps1` exits 0 on re-run |
| 6: New category naming guardrails | `^[a-z][a-z0-9-]+$` (dir), `^[a-z][a-z0-9-]{1,7}$` (spec-id), globally unique |
| 7: Semantic category matching | 4-tier classifier (EXACT→CLOSE→AMBIGUOUS→NO MATCH) with 3-condition hysteresis bias |
| 8: Phased execution model | Phase 1 parallel reads → Phase 2 plan/clarify → Phase 3 parallel writes; ▶/✓/✗ markers |
| 9: Privacy guardrail | No raw transcript text, speaker names, or attribution in generated spec files |
| 10: Failure mode differentiation | Unreadable/empty → abort with error; zero-signal → warn + ask confirmation |

## Phase 1: Design & Contracts

### Data Model

Full entity definitions in `data-model.md`. Key entities:

| Entity | Purpose |
|---|---|
| `TranscriptDocument` | Input: file path, content, inferred metadata |
| `CategoryCatalog` | In-memory snapshot from `specs.yaml` + all `_categories.yaml` |
| `PhaseContext` | Phase tracking, progress markers, error state across all 3 phases |
| `PhaseProgressMarker` | Per-group write progress (▶/✓/✗ with group key + action + status) |
| `IngestionManifest` | Structured list of proposed spec entries + new category proposals |
| `SpecEntry` | One proposed spec file (tier, category, spec-id, requirements, constraints) |
| `NewCategoryProposal` | Registration data for a new category (name, spec-id, description, justification) |
| `GeneratedSpec` | In-memory spec before disk write (frontmatter YAML + body markdown) |
| `IngestionResult` | Final outcome: counts, errors, promotion reminder |

### API Contracts

Full contracts in `contracts/ingest-transcript-cli.md`. Summary:

**Agent execution phases** (normative sequence per REQ-021):

| Phase | Name | Key Output |
|---|---|---|
| 1 | Context Build | Parallel reads; "Context loaded" banner |
| 2 | Plan & Clarification | Grouping plan; Q&A (max 5); conflict resolution |
| 3 | Parallel Write Execution | ▶ start / ✓ success / ✗ error markers; session summary |

**Context loaded banner** (Phase 1 output):
```
✅ Context loaded
└─ Transcript:  <filename> (<N> words)
└─ Tiers:        <T> tiers in catalog
└─ Categories:   <C> categories registered
└─ Existing specs loaded: <S>
└─ UPDATE candidates: <tier>/<category>, ...  (or: none)
```

**Script 1: `register-category.ps1`**  
Parameters: `-Tier`, `-CategoryName`, `-SpecId`, `-Description` (all required)  
Exit codes: 0 (success/idempotent), 1 (validation failure)

**Script 2: `write-spec.ps1`**  
Parameters: `-Tier`, `-Category`, `-SpecId`, `-FrontmatterJson`, `-BodyMarkdown` (all required); `-Force` (optional)  
Exit codes: 0 (written), 1 (validation/path-traversal failure), 2 (file exists + no `-Force`, not an error)  
Guards: `status: draft` enforced regardless of input; path traversal check on target path

### Quickstart

Complete 3-phase walkthrough in `quickstart.md`. Key UX checkpoints:
- Phase 1 completes with context banner (word count, UPDATE candidates)
- Phase 2 grouping plan shows CLOSE MATCH rationale and NEW CATEGORY hysteresis justification inline
- Phase 3 posts `▶ Processing N groups` header then per-group start + completion markers
- Session summary ends with `📝 All output specs are status: draft and require human review before promotion`
